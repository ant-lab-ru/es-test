# es-test

Автоматическая проверка заданий образовательной программы «Встраиваемые системы» от команды [ant-lab](https://ant-lab.ru/).

Сами задания и теория курса — в книге [ant-lab-ru/es-book](https://github.com/ant-lab-ru/es-book): Obsidian-хранилище с картой понятий, картой навыков, теорией и практикой разработки под микроконтроллеры.

Проверка запускается на серверах GitHub, читает ваш репозиторий с проектами курса и отвечает списком пунктов на русском языке: что проверялось и что получилось. Она сообщает расхождение с требованием задания — искать причину и править остаётся вам.

## Как подключить

Подробный порядок — в задании «п1.1.5 Настройка автоматической проверки». Коротко: в свой репозиторий вы кладёте несколько коротких файлов-вызовов, а тело проверки остаётся здесь и подтягивается автоматически. Готовые файлы лежат в [student/.github/workflows/](student/.github/workflows/) — по одному на задание.

Обновлять их не нужно: когда проверка исправляется здесь, исправление действует сразу для всех.

Результат проверки можно отправлять в личный кабинет курса — там можно отслеживать свой прогресс. Для этого в репозиторий кладётся личный секрет (`ES_ACCOUNT_SECRET`), который можно получить, подав заявку на сайте [es.ant-lab.ru](https://es.ant-lab.ru). Без секрета проверки работают как обычно: шаг отправки молча пропускается, а результат остаётся на вкладке `Actions`.

Часть проверок занятия 2.1 смотрит не в текст программы, а в **собранный образ**: какую секцию компилятор отвёл объекту и сколько байт занимает структура. Такие пункты не обмануть правкой комментария, и они не зависят от того, как именно вы назвали переменные в отчёте.

Проверка запускается на сервере, где вашей платы нет, и сама она устройство не видит. Начиная с занятия 1.3 работу прошивки на плате подтверждает **лог прогона**: у себя на компьютере вы запускаете Python-скрипт задания, он опрашивает подключённую плату по USB и записывает обмен в файл рядом с проектом. Файл уезжает в репозиторий вместе с кодом, а проверка читает его и убеждается, что прошивка отвечала так, как требует задание, — и что на другом конце провода была Raspberry Pi Pico: в шапке лога стоят её код USB-устройства и серийный номер.

Лог — свидетельство прогона, а не доказательство: файл лежит у вас и вы вправе написать в нём что угодно. Смысл в другом — довести задание до работающей платы и увидеть её ответы своими глазами.

## Прогнать у себя

Те же проверки работают на вашем компьютере — не дожидаясь отправки в репозиторий и не тратя минуты GitHub. Для этого репозиторий с проверками нужно склонировать себе, рядом со своим:

```
Repositories
└── pico
    ├── es-student     ← ваш репозиторий
    ├── es-test        ← проверки
    └── pico-sdk
```

Дальше выберите свою систему и выполните команды подряд — они разные, смешивать их не нужно.

### macOS и Linux

Подойдёт стандартный терминал системы.

1. Перейдите в рабочую папку курса и склонируйте проверки:

``` bash
cd ~/Repositories/pico
git clone https://github.com/ant-lab-ru/es-test.git
```

2. Запустите проверку, передав путь к своему репозиторию:

``` bash
cd es-test
./run-local.sh ../es-student          # все проверки занятия
./run-local.sh ../es-student 1.1.2    # одна проверка
```

Переменную `PICO_SDK_PATH` задавать не нужно: вы настроили её в задании п1.1.1, и терминал берёт её сам.

### Windows

Нужен **Git Bash** — он ставится вместе с Git. PowerShell проверки не запустит: они написаны на bash. Откройте меню «Пуск», наберите `Git Bash` и запустите его; либо щёлкните правой кнопкой по папке и выберите «Open Git Bash here».

1. Перейдите в рабочую папку курса и склонируйте проверки:

``` bash
cd /c/Repositories/pico
git clone https://github.com/ant-lab-ru/es-test.git
```

2. Запустите проверку, передав путь к своему репозиторию:

``` bash
cd es-test
./run-local.sh ../es-student          # все проверки занятия
./run-local.sh ../es-student 1.1.2    # одна проверка
```

Переменную `PICO_SDK_PATH` задавать не нужно: вы настроили её в задании п1.1.1, и Git Bash берёт её из Windows сам.

> [!IMPORTANT]
> Диск в Git Bash пишется как `/c/…`. Привычная запись с обратными слешами — `C:\Repositories\pico` — здесь не сработает: bash понимает `\` как экранирование и склеит путь в бессмыслицу. Это особенность только Git Bash — в PowerShell, где вы собираете проект по заданиям курса, пути пишутся как обычно.

### Дальше одинаково

Если проверки `1.1.2` и `1.1.3` сообщают «не задан PICO_SDK_PATH», значит терминал не видит переменную из задания п1.1.1 — те проверки, что читают файлы, отработают, а сборка прошивки нет. Посмотрите, что в ней:

``` bash
echo $PICO_SDK_PATH
```

Пустой ответ означает, что переменная не задана или терминал открыт раньше, чем она появилась: перезапустите терминал, а если не помогло — вернитесь к шагу 4 задания п1.1.1. В Windows команда напечатает путь в обычной форме, `C:\Repositories\pico\pico-sdk`, — так и должно быть, переделывать его в `/c/…` не нужно.

Когда проверки обновятся, свежую версию можно будет получить командой `git pull` в папке `es-test`. В GitHub Actions это происходит само, в процессе автоматической проверки клонируется последняя версия репозитория.

## Что где лежит

- [checks/](checks/) — скрипты проверок, общий отчёт `lib/report.sh`, сборка проекта `lib/build.sh`, имя проекта в описании сборки `lib/cmake.sh` и чтение лога прогона на плате `lib/device.sh`.
- [.github/workflows/](.github/workflows/) — тело проверок, вызываемое из вашего репозитория.
- [.github/actions/pico-toolchain/](.github/actions/pico-toolchain/) — установка ARM GCC, Pico SDK и picotool на машине проверки.
- [student/.github/workflows/](student/.github/workflows/) — файлы, которые вы копируете к себе в репозиторий es-student.
- [run-local.sh](run-local.sh) — локальный прогон.
